# 運用手順

## 1. 本番への反映(画面・BFF・api-server・Moodleイメージ)

**手でデプロイしません。master へのマージで自動的に本番に出ます。**

1. `dev/kanegae` で修正して push する(画面は dev プレビューで確認できる)
2. `dev/kanegae` を `master` へマージして push する
3. GitHub Actions が自動で動く
   - `frontend/` が変わったとき → `Deploy Frontend`(S3 と CloudFront を更新。約3分)
   - `bff-server/` `api-server/` `nginx/` `moodle-app/` が変わったとき → `Deploy Backend and Moodle App`
     (イメージを作って ECS を1台ずつ入れ替え。10〜15分)
4. 結果を確認する
   ```
   gh run list --branch master --limit 6
   ```
   すべて `success` ならOK。

**失敗したとき**: ECS は新しい版が起動しなければ自動で元の版に戻ります(サービスは止まりません)。
画面に問題が出たときは、master で該当のマージを `git revert` して push すれば前の版が出ます。

> Moodle の**自作プラグイン**(`moodle-app/customizations/local/`)だけは、この流れでは本番に届きません。
> 3章を見てください。

## 2. 本番のインフラ(cdk-prod)を変えたとき

`cdk-prod/lib/*.ts` などインフラの定義を変えたときだけ、手で反映します。
**`cdk deploy` を直接打たず、必ずスクリプトを使ってください。**

```
cd cdk-prod
./scripts/deploy-prod.sh diff   prod-EcsStack   # 差分を見るだけ(本番は変わらない)
./scripts/deploy-prod.sh deploy prod-EcsStack   # 差分を見せてから、スタック名を入力すると反映
```

- 1回に1スタックだけ反映します。必須の値(台数=2、最新のイメージ、教材認証の鍵など)はスクリプトが入れます
- 差分に **削除(`[-]`)や作り直し(`[-/+]`・replacement)** が出ていたら反映せず、詳しい人に相談してください
  (`AWS::ECS::TaskDefinition` の replace だけは新しい版の登録なので問題ありません。
  イメージのタグだけが変わる差分は、GitHub Actions が先に反映した版を CDK 側の記録に合わせるもので、これも問題ありません)
- 慣れないうちは diff までにして、deploy は詳しい人と一緒に行ってください

## 3. Moodle の自作プラグインを更新するとき

本番の Moodle は、イメージを更新してもプラグインが入れ替わりません(Moodle のファイルは EFS にあり、
イメージからコピーされるのは最初の起動時だけ)。毎回 EFS に直接置く必要があります。

大まかな流れ(**必ず詳しい人と行う**):
1. 本番DB(`prod-lms-db`)のスナップショットを取る
2. プラグインのファイルを ECS の moodle-app コンテナ経由で EFS に展開する
   (`docker exec -u daemon` で、`tar --no-same-owner` で展開する。root では所有者を変えられない)
3. `admin/cli/upgrade.php --non-interactive` を実行する
4. 新しい関数を足したときは `scripts/db/add-webcoach-utils-functions-to-moodle-api-service.sql` を流す
   (BFF が使うサービス `moodle-api-service` に関数を登録する。忘れると BFF からの呼び出しが失敗する)

dev 環境(EC2)も同じで、git を更新しただけではプラグインは入れ替わりません。

## 4. dev 環境への反映

- 画面: `dev/**` ブランチへ push すると自動でプレビューに出る
- BFF・api-server: 自動では出ない。EC2 `dev-moodle-docker` で手動反映する
  ```
  # SSM で EC2 に入り、/home/ec2-user/moodle-docker で
  git pull origin dev/kanegae
  export DOCKER_BUILDKIT=0 COMPOSE_DOCKER_CLI_BUILD=0   # これが無いとビルドが黙って失敗する
  docker-compose build api-server bff-server
  docker-compose up -d api-server bff-server
  ```
  出力に `Recreated` が出れば成功。`Running` のままなら古い版のままです。

## 5. 本番の起動・停止

**本番は受講生が利用中です。普段は止めません。** 自動停止のスケジューラも止めてあり、有効にしてはいけません。

障害対応などで必要なときは Claude Code の運用スキルを使います(手で ECS や RDS を操作しない)。

| やりたいこと | スキル | 備考 |
|---|---|---|
| 本番DBを起動 | `start-prod-rds` | ECS より先に起動する |
| 本番ECSを起動 | `start-prod-ecs` | |
| 本番ECSを停止 | `stop-prod-ecs` | 全員が使えなくなる。責任者の指示があるときだけ |
| 本番DBを停止 | `stop-prod-rds` | ECS を止めてから |
| dev EC2 を起動・停止 | `start-dev-moodle-ec2` / `stop-dev-moodle-ec2` | |
| UAT DB を起動・停止 | `start-uat-rds` / `stop-uat-rds` | dev もこのDBを使う |

止めるときは ECS → RDS、起動するときは RDS → ECS の順です。
起動・停止は Lambda `prod-ecs-scheduler` / `prod-rds-scheduler` 経由で行います
(正しい順序で台数を戻す処理が入っているため。ソースは `cdk/lambda/`)。

## 6. Slack に通知が来たとき

| チャンネル | 来るもの |
|---|---|
| `#lms-alert` | 本番ログのエラー、アラーム(ALBの5xx・DBの容量など)、ECSタスクの停止、GuardDuty(不正アクセスの検知)、月の予算超過 |
| `#lms-cost-reporting` | 毎朝の利用状況・費用のレポート |

`#lms-alert` に来たら:
1. 同じエラーが続いているか、1回だけかを見る(1回だけで画面が使えていれば急がない)
2. 受講生から問い合わせが来ているか確認する(`docs/support/` も参照)
3. 詳しく見るときは CloudWatch Logs のロググループ `/ecs/prod/lms` を Logs Insights で検索する
4. 判断できなければ詳しい人に、通知の内容をそのまま送る

既知の「気にしなくてよいもの」:
- moodle-app の `invalidsesskey`(約10分おき。通知対象外)

## 7. 設定の変更・期限の確認(LMS管理画面)

- **動作設定**: AIのトークン上限・リマインドメールや議事録取り込みのオン/オフなど。保存後に画面の
  「再起動」ボタンで反映(本番は Parameter Store `/lms/prod/...` に保存される)
- **期限管理**: 証明書・Google連携などの期限を一覧で確認できる。月に1回は見る
- **受講生の状態確認**: 問い合わせ対応用(`docs/support/README.md` 参照)
