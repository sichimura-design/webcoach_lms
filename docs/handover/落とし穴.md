# 落とし穴(知らないと事故になること)

どれも過去に実際に起きたか、起きかけたものです。

## 本番のインフラ(cdk-prod)

- **`cdk deploy` を直接打たない。`cdk-prod/scripts/deploy-prod.sh` を使う**。以下はスクリプトが防いでいる事故です
  - `prod-EcsStack` の台数(desiredCount)を 0 にすると本番が止まる。スクリプトは常に 2 を渡す
  - `imageTag` が古いコミットだと本番が昔の版に戻る(別の人が古い値で反映し巻き戻ったことがある)。
    スクリプトは origin/master の最新に固定する
  - 依存スタック(VPC・ALB・Backend)まで一緒に更新される。スクリプトは1スタックだけ反映する
  - `prod-SpaStack` に `contentTokenSecret` を渡し忘れると、教材HTMLの表示が全件失敗する
  - `prod-GithubActionsStack` は既定値が `REPLACE_ME` で、反映すると自動デプロイの権限が壊れる
- `/usr/bin/cdk`(古い)では cdk-prod のライブラリを読めない。`cdk-prod/node_modules/.bin/cdk` を使う
- `cdk/` `cdk-dev/` `cdk-uat/` は dev/uat 用。**本番は `cdk-prod/` だけ**
- `prod-EcsStack` の反映で EC2 の自動起動グループ(ASG)が作り直され、EC2 が余分に起動することがある。
  反映後に台数(2台)を確認する
- `prod-AlbStack` でターゲットグループ(`prod-lms-tg`)が作り直し(replace)になる差分が出たら反映しない。
  名前が固定のため衝突して失敗し、スタックが戻る(2026-09 に一度起きた)
- AWS CLI は `--profile PowerUserAccess-...` か `AWS_PROFILE` を付けないと、認証切れのようなエラーになる

## 本番の Moodle

- **自作プラグインはイメージを更新しても本番に入らない**(EFS に直接置く。`運用手順.md` 3章)
- プラグインに関数を足したら、サービス `moodle-api-service` にも登録する
  (`scripts/db/add-webcoach-utils-functions-to-moodle-api-service.sql`)。プラグイン自身のサービスに登録されても、
  BFF が使っているのは `moodle-api-service` なので呼べない
- Moodle の「保留中のアップグレードなし」表示は当てにならない(コードが無いプラグインは数えられない)

## 本番は2台で動いている

- ECS は2台で、どちらにリクエストが行くか分からない。プロセスのメモリに状態を持つ処理(AIチャットの会話など)は、
  ALB のスティッキー(同じ人は1日同じ台へ)で成り立っている。台の入れ替え(デプロイ・再起動)時は AI 処理中の状態が消える
- 定期処理(議事録の取り込み・リマインドメール)は DB のロックで「担当の1台」だけが動く。新しい定期処理を足すときも同じ仕組みに乗せる

## dev 環境

- **dev と UAT は同じDB(`uat-moodle-db`)を使っている**。dev でテーブルを変えると UAT にも効く
- dev の BFF・api-server は自動で更新されない(`運用手順.md` 4章)
- dev EC2 で `docker-compose build` は `DOCKER_BUILDKIT=0` を付けないと黙って失敗し、古いまま再起動する
- BFF に npm パッケージを足したときは、`docker-compose rm -f -v bff-server` → `docker-compose up -d --renew-anon-volumes bff-server`
  で作り直す(古い node_modules が残って起動しない)
- dev EC2 のコンテナ(moodle-api 等)の中で重い処理を走らせない。メモリ上限で api-server が落ちる
- dev プレビューで「直したのに古い画面が出る」ときは、まずブラウザのスーパーリロード

## コード

- 画面には **モック(MSW)** があり、dev プレビュー以外の実バックエンドには無い項目がモックには入っていることがある。
  「モックでは動くが本番で0件・読み込み中のまま」はこれを疑う
- 新しいDBテーブル・カラムを足す前に必ず相談する(本番DBへの反映が手作業になるため)
- Moodle のログ(`mdl_logstore_standard_log.timecreated`)は Unix 秒。`TIMESTAMPDIFF` に直接渡すと NULL になる
- コーチングの「実施済み」を status だけで判定しない(コーチが結果を記録しないことが多く、過去の回もほぼ NULL)

## 調べ方のコツ

- 本番のエラーは CloudWatch Logs `/ecs/prod/lms` を Logs Insights で検索するのが早い
- ログイン失敗の原因(パスワード間違い・期限切れなど)は CloudTrail の Cognito の記録で分かる
- 調査はまず手元のソースを grep する。ブラウザや AWS を1件ずつ叩くより早い
