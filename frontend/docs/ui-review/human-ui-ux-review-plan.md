## 0. 実施順と、指摘の3分類（2026-08-27 追加）

### なぜフェーズ5を最初に回すのか

色・余白・ボタン・カード・文言のばらつきは **画面固有の問題ではなく横断課題**です。
これを画面ごとのレビュー（フェーズ2）で拾うと、**同じ指摘が画面数ぶん重複して出て、修正も画面数ぶん発生します**。
フェーズ5（CONSISTENCY-001〜007）は最初から「観点を1つ固定して複数画面を横に並べて比べる」構成になっているので、
**ここを先に回すと、横断課題が重複なくまとめて出ます**。フェーズ2以降は、それを差し引いた
「その画面にしかない問題」に集中できます。

### 指摘は必ず3分類する

記録時に **分類** 列（§5.1）へ A / B / C を入れてください。**修正の進め方が分類ごとに違います。**

| 分類 | 中身 | 修正の単位 |
|---|---|---|
| **A: 横断** | 色・余白・文字サイズのばらつき、ボタン／カードの実装差、モーダルの閉じ方、空・読み込み・エラー表示の欠落、用語のばらつき | **画面ごとに直さない。** トークン／共通部品／規約を1箇所直す |
| **B: 画面固有** | 情報設計、その画面の文言、導線、そこにしかない違和感 | 画面ごと |
| **C: 教材語彙** | 移行教材（Clipkit由来）の本文の見た目 | HTML の class 単位（1つ直すと全レッスンに効く） |

判断に迷ったら **「他の画面でも同じことが起きているか」を1つ確認**してください。起きていれば A です。

### 確認する画面幅は3つに固定する

毎回この順で見てください。**表内の「画面サイズ」欄が 1440px 単数指定になっているタスクも、この3幅で見ます。**

| 幅 | 位置づけ |
|---|---|
| **1920px** | 等倍。デザインの基準幅（1900px）に最も近い |
| **1520px** | **最も崩れる幅。ここを飛ばさないこと。** Windows の表示倍率125%で CSS 上の可視幅がこの値まで落ちるため、実際の利用環境の多数がここに当たる（根拠: `frontend/src/index.css` の可変スケール節のコメント） |
| **390px** | スマホ。フェーズ4（DEVICE-*）の 375px 指定もこの幅に読み替えてよい |

## この文書の読み方

- この文書は **Claude Code がリポジトリを調査して作った「レビューの段取り」** です。UI/UX の良し悪しの結論は一切書いていません。
- **「コードから分かる事実」** と **「人が画面を見ないと判断できないこと」** を明示的に分けています。
  - 🧾 **事実** = コードを読めば確定すること（ルート、状態分岐、レイアウト方式など）
  - 👁 **要目視** = 実際に触らないと判断できないこと（迷うか、分かるか、目立つか）
- チェックボックスは表の中では `☐` で表記しています（表の外では `- [ ]` を使用）。
- **レビュー中はコードを変更しないでください。** 気づいたことは指摘IDを付けて記録だけします。

### 両環境で共通の前提

- モックは ON（`REACT_APP_ENABLE_MOCKS=true`）。実 Cognito / 実 BFF には接続しません。
- ログインは **任意のメールアドレス・任意のパスワード** で成功します（`frontend/src/mocks/mockAuth.ts`）。
- 未ログイン状態に戻したいとき: DevTools → Application → Local Storage → `webcoach-mock-logged-in` を削除。
- **モックデータを初期状態に戻したいとき**: DevTools → Application → Storage → **Clear site data** → リロード。
  （学習記録・ノート・コーチング目標は localStorage 永続。学習ロードマップ・コーチングセッションはメモリ保持なのでリロードで初期化。AIコーチの会話は sessionStorage なのでタブを閉じると消える。）

### 複数人でレビューするときの注意

1. **モックデータはブラウザごとに独立しています。** サーバー側に共有の状態はありません。学習記録・ノート・タイマーの記録はレビュアーごとに別物になるので、「ノートが3件ある」等の前提は各自で作ってください。
2. **開始前に全員が Clear site data を実行してください。** これをしないと、人によって初期状態が違ったまま比べることになります。
3. **全員が「管理者＋コーチ」権限で入ります**（モックの仕様。§1.1 参照）。サイドバーに出る「管理」は、本番の受講生には出ない項目として無視してください。
4. **プレビューは最後に push した内容です。** 画面を直したら push しないとレビュアーには反映されません。逆にレビュー期間中は、断りなく push しないほうが安全です（見ている画面が途中で変わります）。
5. **指摘は全員が同じ表に記録します**（§5.1）。誰の指摘か分かるよう、指摘IDの後ろに記入者のイニシャルを付けるか、記録表に「記入者」列を足してください。

# 1. LMS構造の調査結果

## 1.1 ユーザー種別

`frontend/src/routes/index.tsx` の `ProtectedRoute` / `AdminRoute` / `CoachRoute` と、`AuthContext` の Cognito グループ判定（`admin` / `coach`）から確定した種別です。

| # | ユーザー種別 | 判定条件（コード上） | 到達できる画面 | モックで再現できるか |
|---|---|---|---|---|
| 1 | 受講生（学習者） | ログイン済み・グループなし | 学習系すべて（`/mypage` 〜 `/notes`） | ○（ただし後述の注意あり） |
| 2 | コーチ | Cognito グループ `coach` | 受講生と同じ画面 ＋ `/coach/students` | ○ |
| 3 | 管理者 | Cognito グループ `admin` | 受講生と同じ画面 ＋ `/admin/*` | ○ |
| 4 | 未ログインユーザー | セッションなし | `/login`, `/password-reset`, `/connect/:token` のみ。他は `/login` へリダイレクト | ○ |
| 5 | コーチ（LMSアカウントなし） | 認証不要。`/connect/:token` だけ ProtectedRoute の外に置かれている | `/connect/:token` の1画面のみ | △（有効なトークンが必要） |

**組織管理者・保護者・講師（コーチとは別）といった種別は、リポジトリ上に存在しません。**

> 🧾 **事実（重要）**: モック認証の擬似ユーザーは `MOCK_GROUPS = ['admin', 'coach']` 固定です（`frontend/src/mocks/mockAuth.ts:17`）。
> つまり **モックのままログインすると常に「管理者かつコーチ」** になります。
> 純粋な受講生視点にするには `MOCK_GROUPS` を `[]` にする必要があります（ファイル冒頭のコメントにも明記されています）。
>
> ただし、権限による画面差は **サイドバー／SP下部ナビの「管理」または「受講生一覧」項目が出るかどうかだけ** です（`AppHeader.tsx` の `manageItems`）。
> それ以外の画面・文言・データは受講生と完全に同一です。
> → **運用方針**: 通常のレビューは既定のまま行い、「サイドバーに『管理』が出ているのは、本番の受講生には出ない」と読み替えてください。受講生専用の見え方を厳密に見たい日（DEVICE-006 / CONSISTENCY-002）だけ、レビュー開始**前**に `MOCK_GROUPS` を `[]` に変更し、その日の終了後に戻します。この変更はレビュー作業ではなく環境準備として扱います。

## 1.3 主要ユーザーフロー（モックに実在するものだけ）

受講生（最重要ユーザー）:

1. **F1 入場して次にやることを知る**: `/login` → `/mypage`
2. **F2 前回の続きから学習を再開する**: `/mypage`（続きからはじめる）→ `/course/:id/curriculum` → `/course/:id?module=`
3. **F3 レッスンを読み切って完了し、次へ進む**: 学習ワークスペース内（本文 → 完了 → 次のレッスン）
4. **F4 学習したいコースを自分で探す**: `/courses`（検索・領域ジャンプ）→ コーストップ → レッスン
5. **F5 集中して学習し、記録を残す**: `/focus-booth`（開始 → 終了カード）→ `/study-log`
6. **F6 分からないことをAIに聞き、後で振り返る**: レッスン本文選択 → 解説／質問／クリップ → `/notes` → 元のレッスンへ戻る
7. **F7 長期の学習計画を作る**: `/learning-plan/setup`（8問）→ プレビュー → `/learning-plan`
8. **F8 計画を見直す**: `/learning-plan`（更新案カード／4問チェックイン）→ 反映
9. **F9 コーチングを受けて目標を確定する**: `/coaching`（リンク登録 → 参加 → 終了 → 生成中 → 要約確認 → 目標確定）→ `/mypage` に反映
10. **F10 AI専用ページで相談する**: `/ai-coach`（ホーム → 機能選択／自由入力 → 会話 → 履歴）

コーチ:

11. **F11 担当受講生の状況を見る**: `/coach/students`

# 2. レビュー対象の優先順位

## 最優先: 受講生 × 「前回の続きから学習して、1レッスンを完了する」（F1→F2→F3）

理由:

1. **利用頻度が圧倒的に高い。** LMSの受講生は毎回このフローを通ります。ここで迷うと他のどの改善も効きません。
2. **画面が最も作り込まれている。** マイページ・学習コンテンツ・コーストップ・学習ワークスペースは直近のコミット（`ce4e844`, `2d6af16`, `0ab8ba0`）で全面刷新されており、レビューの投資対効果が最大です。
3. **設計意図とのズレを検証すべき箇所が集中している。** マイページのコメントには「以前はカード9枚・データ点70個まで膨らみ、数字が重複していたので主アクションを『続きからはじめる』1つに絞った」と明記されています。**その狙いが実際に伝わっているかは、コードでは判定できません。**
4. 学習ワークスペースは「本文を主役に、目次とAI/メモを必要なときだけ並列表示する」という最も複雑な設計判断を含みます。

## 2番目: 受講生 × 「集中ブースで学習し、記録を振り返る」（F5）と「AI・ノートで理解を補う」（F6）

差別化機能であり、状態遷移が多く（タイマー5状態）、画面をまたぐ数値の整合が体験の信頼に直結します。

## 3番目: 受講生 × 「ロードマップ」「コーチング」（F7〜F9）

新しい機能で情報量が多く、**「これは誰が決めたことか（AIの案か、コーチと決めたことか）」が伝わるか** が最大の論点です。

## 後回し: コーチ・管理者画面

画面数は多いものの、対象人数が少なく、モックが未整備で確認できない範囲が広いためです。

## 5.1 指摘記録表（発見した問題を1行ずつ）

**指摘IDの付け方**: `<タスクID>-<連番>`（例: `FLOW-002-01`, `CONSISTENCY-001-03`）

**分類**（§0 参照）: `A`=横断（他画面でも起きている） / `B`=画面固有 / `C`=教材語彙。
**記入者**: イニシャル。複数人が同じ表に書くので必須。
**幅**: `1920` / `1520` / `390` のどれで見つけたか。**同じ指摘が複数幅で出るなら、その幅を全部書く**（例 `1520,390`）。

| 指摘ID | 分類 | 記入者 | レビュータスクID | ユーザー種別 | ユーザーの目的 | 画面 | 幅 | 操作 | 期待したこと | 実際に起きたこと | 迷い・違和感 | ユーザーへの影響 | 重大度 | 改善案 | スクリーンショット | 備考 |
|---|---|---|---|---|---|---|---|---|---|---|---|---|---|---|---|---|
| FLOW-002-01 | B | SM | FLOW-002 | 受講生 | 前回の続きを開く | /mypage | 1920 | 「続きからはじめる」を押した | レッスン本文が開く | コーストップに着いた | もう1回押す必要があると分かるまで4秒かかった | 毎回1操作増える | 中 | （空欄可） | `FLOW-002_01_mypage_1920.png` | 例です。実際の記録に置き換えてください |
| CONSISTENCY-001-01 | A | SM | CONSISTENCY-001 | 受講生 | ボタンの一貫性を検証する | 全画面 | 1920 | 8画面の主ボタンを並べた | 主ボタンの色が同じ | 3画面だけ色が違った | どれが主ボタンか画面ごとに考え直した | 押す場所の学習が効かない | 中 | （空欄可） | `CONSISTENCY-001_01_buttons_1920.png` | 例です。A分類なので画面ごとには直さない |
|  |  |  |  |  |  |  |  |  |  |  |  |  |  |  |  |  |

**重大度の基準**:

- **高**: 操作が止まる、誤操作する、目的を達成できない
- **中**: 迷う、不安になる、理解に時間がかかる
- **低**: 利用できるが、分かりにくい、気持ちよくない

**記入のコツ**:

- 「期待したこと」は**操作する直前に頭にあったこと**を書きます。操作した後に思い付いた理想像ではありません。
- 「迷い・違和感」には**時間**を書きます（例: 「押す場所を探すのに6秒」「3回見比べた」）。
- 「改善案」は空欄で構いません。**観察した事実を優先**してください。

# 8. レビュー時の注意事項

このセクションは、レビューを始める前に毎回目を通してください。

## 8.1 姿勢

- **実装者としてではなく、設定したユーザーとして操作する。** 「ここはこう作ってあるはず」という知識を一度脇に置きます。
- **最初から改善案を考えない。** まず違和感を記録します。改善案は空欄のままで構いません。
- **迷った時間と、最初に見た場所を記録する。** 「分かりにくい」より「見つけるのに8秒かかり、まず右上を見た」の方が10倍役に立ちます。
- **操作できたことと、迷わなかったことを区別する。** 3秒迷って押せたなら、それは「迷った」です。
- **見た目の好みと、ユーザー体験上の問題を区別する。** 「この赤は好きじゃない」と「主要ボタンが背景に埋もれて見つからない」は別物です。前者は重大度「低」、後者は「高」です。

## 8.2 記録

- **問題がない画面も確認済みとして記録する。** 「問題なし」の記録がないと、見ていないのか問題がなかったのか後で分かりません。
- **発見した問題には必ず指摘IDを付ける。** 形式は `<タスクID>-<連番>`。
- **1つのタスク中に別の問題を見つけても、その場で追いかけない。** 指摘IDを付けて記録し、元のタスクに戻ります。別画面の問題は、その画面のタスクIDで後日改めて記録します。
- **スクリーンショットは「問題が写っている状態」で撮る。** 撮り直しは効きません。

## 8.3 禁止事項

- **目視レビュー中はコードを変更しない。** `MOCK_GROUPS` の変更など環境準備が必要な場合は、レビュー**開始前**に行い、**終了後に戻します**。
- **DevTools で DOM やテキストを書き換えて検証しない。** それは実装検証であり、目視レビューではありません（気づいたことは「観点」として記録）。
- **1日の予定量を超えて続けない。** 疲れた状態のレビューは「慣れ」が生まれ、初見の違和感を拾えなくなります。

## 8.4 中断・再開のルール

- タスクの途中で中断した場合は、**そのタスクを最初からやり直します**（フローの途中からでは「迷うかどうか」が判定できないため）。
- 日をまたぐときは、必ず §5.2 のタスク進捗表を更新してから終わります。
- 翌日は、前日のメモ「明日確認したくなったこと」を読んでから始めます。
